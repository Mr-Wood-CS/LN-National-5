# Development Methodologies

!!! info "What you need to know"

    At National 5, you should be able to describe and apply the six stages of the iterative development process when solving a programming problem.

In **iterative development**, you revisit earlier stages as you learn more about the problem or find a fault. For example, a failed test can send you back to **implementation** if the code differs from the design, or back to **design** if the planned algorithm is wrong. After making the change, run the test again to check the result. [National 5 Computing Science specification, page 4](https://www.sqa.org.uk/sqa/files_ccc/n5-course-spec-computing-science.pdf#page=5)

## The six stages of development

| Stage | What you do |
| --- | --- |
| **Analysis** | Identify the purpose of the program and its functional requirements. Work out the inputs it needs, what processing it must carry out and what outputs it must produce. |
| **Design** | Plan the solution before coding. Choose suitable data types and structures, such as an integer for a whole-number score or a one-dimensional array for a collection of scores. Plan the algorithm using pseudocode, a flowchart or a structure diagram. Use a wireframe when you need to plan the user interface. |
| **Implementation** | Turn the design into code. Run the program as you build it to check that each part behaves as intended. |
| **Testing** | Choose inputs based on the requirements. Predict the expected results, run the program and compare its actual results with your predictions. Retest when you make a change. |
| **Documentation** | Record how the program works and how to use it. Keep the design, test results and relevant code comments up to date as the program changes. |
| **Evaluation** | Judge the solution using evidence. Consider fitness for purpose, efficient use of coding constructs, robustness and readability. |

## Worked example: validating a quiz score

A teacher needs a program that accepts a whole-number quiz score from **0 to 10 inclusive** and displays an error message for scores outside that range.

**Analysis.** The input is a whole-number score. The program checks whether it is in range and displays either **Score accepted** or **Invalid score**.

**Design.** Store the score as an integer. Accept it if it is greater than or equal to 0 and less than or equal to 10.

**Implementation.** The first version uses `score >= 0 and score < 10`. The upper comparison in the code leaves out 10.

**Testing.** The test with 5 passes, but the test with 10 fails. The developer checks the design and finds that it correctly includes 10. They return to **implementation** and change `score < 10` to `score <= 10`.

| Test input | Type | Expected output | Before the fix | After the fix |
| --- | --- | --- | --- | --- |
| `5` | Normal | Score accepted | Score accepted | Score accepted |
| `0` | Extreme | Score accepted | Score accepted | Score accepted |
| `10` | Extreme | Score accepted | Invalid score | Score accepted |
| `11` | Exceptional | Invalid score | Invalid score | Invalid score |

The developer first retests 10 to check the fix. Then they rerun the other tests to check that the change still accepts valid scores and rejects 11.

**Documentation.** Record the failed test, the corrected comparison and the retest results. If the design or user instructions change during development, update those too.

**Evaluation.** The retest shows that the program now accepts the upper boundary and still rejects the score immediately above it. This supports the judgement that the validation works for the whole-number inputs tested.
