# Testing SQL Operations

Predict the result from known records before running a query. Compare the actual result with the prediction. For a `SELECT`, check which rows appear, which fields are shown, and how the rows are ordered.

## Worked example

The [Bakery query](../4.4-implementation/3.4.3-sql-equi-joins.md) should show Glasgow products costing under £2, cheapest first, with names used to break ties.

| What to check | Expected result | Actual result |
| --- | --- | --- |
| Matching rows | Morning roll, Empire biscuit and Oat biscuit | All three appear. |
| Excluded rows | Fruit scone is from Greenock. Sourdough loaf costs 350 pence. | Neither appears. |
| Output fields | Product name, price in pence and bakery name | All three fields appear. |
| Sort order | Morning roll first. Empire biscuit before Oat biscuit at the same price. | The rows appear in the predicted order. |

For a boundary test, a product in Glasgow priced at exactly 200 pence should be excluded. That case checks the difference between `< 200` and `<= 200`.

## Testing changes to records

Run a `SELECT` before and after an `INSERT`, `UPDATE` or `DELETE` to check the effect. In the Shortbread examples, product 106 should appear after the insert, have a price of 125 pence after the update, and disappear after the delete. Compare the other records too, especially when checking that an update or delete affected only the intended row.
